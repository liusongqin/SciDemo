## 整体安排

## 第 1 页｜项目原理：把一句提问，变成可检查的求解过程

### 本页回答的问题

Agent 是什么？SciDemo 帮学生完成什么？

### 屏幕上放什么

主标题：**把一句提问，变成可检查的求解过程**。

引入案例：学生提出“求 x²−2=0 的正数解，并说明怎么检查”。

案例结果：工具计算得到 `x ≈ 1.41421356`，再代回原式检查差值。

核心公式：**Agent = 模型决策 + 工具执行 + 状态记录 + 反馈循环**。

一句话原理：**模型读取目标与已有结果，决定调用什么工具，以及是否继续。**

### 画面怎么放

左侧放学生的问题与近似结果；右侧用“读目标 → 选工具 → 看结果 → 再决定”四个节点构成循环。底部用四个短标签列出 Agent 的组成。

### 建议讲解稿

这个项目把语言模型、科学计算工具和任务流程组织成一位学习助手。学生提出一道题后，系统不仅展示答案，还展示它选了什么工具、工具返回了什么、结果怎样被检查。例如求 x²−2=0 的正数解，模型提出工具调用请求，后端运行真正的求根函数，再检查代回原式的差值。模型读到这份结果后，决定继续计算还是整理解释。Agent 的自主性，就体现在这种根据结果决定下一步的能力上。

### 学生带走的一句话

**模型提出动作，程序执行计算，结果影响下一步。**

## 第 2 页｜协作机制：四个角色如何交接与循环

### 本页回答的问题

四个 Agent 分别负责什么？它们怎样完成同一个任务？

### 屏幕上放什么

主标题：**四种职责，共同推进一道题**。

| 角色 | 页面上的简短职责 |
| --- | --- |
| 问题分析员 | 读懂条件与目标 |
| 科学求解员 | 选择工具，根据结果决定下一步 |
| 验证审查员 | 程序验算，再由模型复核当前步骤 |
| 报告撰写员 | 根据已验证记录组织说明 |

交接关系：**分析员 → 求解员 → 审查员 → 求解员**；求解员决定可以汇总时，交给报告员。

两条关键说明：

- **当前步骤通过 = 程序检查通过，且模型复核同意。**
- **四种角色可以共用同一个模型，分开的是职责。**

### 画面怎么放

四个角色排成一行。分析员指向求解员，求解员把计算结果送给审查员；审查员用回流箭头把证据送回求解员。单独画“求解员 → 报告员”的上方分支，避免误画成审查员直接决定整题结束。

### 建议讲解稿

四个角色像一个有分工的学习小组：分析员读题，求解员选择工具，审查员验收当前计算步骤，报告员解释已有证据。审查员先运行程序检查，再请模型阅读证据；程序失败时，模型不能将它改成通过。无论当前步骤通过还是需要修正，结果都会交回求解员，判断后续还要做什么。它认为可以汇总时，再交给报告员。四种角色可共用同一个模型，通过不同的任务说明和共享记录完成协作。

### 学生带走的一句话

**检查的是当前步骤，推进整个任务由求解员继续判断。**

## 第 3 页｜系统架构：模型、工具和记录如何配合

### 本页回答的问题

网页背后的主要部件是什么？谁负责协调？

### 屏幕上放什么

主标题：**流程控制中心，把各个部件串起来**。

- **网页界面**：提问、看进度、看结果、参与审核。
- **流程控制中心**：安排角色、校验动作、传递结果、控制循环。
- **语言模型**：理解、选择、审阅与解释。
- **科学工具与验算**：运行允许的数学函数，提供计算及检查证据。
- **任务记录**：保存问题、结果、验证与事件历史。

技术名称用小字标注：Vue；FastAPI + LangGraph；默认本地 Qwen / vLLM；SymPy / SciPy / NumPy；SQLite。

部署说明：**应用部署在内网；公网只转发访问请求。**

### 画面怎么放

上层放“网页界面 ↔ 流程控制中心”，下层放模型、计算与验算、任务记录三个框，由控制中心分别连接。公网转发作为底部部署说明，不把端口和运维命令放进主图。

### 建议讲解稿

学生看到的是网页。网页把问题交给接口服务，流程控制中心负责安排后续步骤：什么时候调用模型，什么时候执行工具，什么时候检查和记录。模型不会自己执行计算函数，而是把工具请求交给后端校验和执行。任务记录让下一轮能够读到已有结果；事件流把工具调用、检查和角色交接等进度持续传回页面。模型的上下文由系统整理，长期任务记录保存在后端。部署时，前端文件、后端和模型均在内网，公网仅负责转发。

### 学生带走的一句话

**网页负责呈现，流程负责协调，模型与计算程序各司其职。**

## 第 4 页｜开发演进：先跑通闭环，再逐步增加自主性

### 本页回答的问题

为什么采用分阶段开发？每一步解决什么问题？

### 屏幕上放什么

主标题：**每增加一点自主性，就补相应的检查与记录**。

| 阶段 | 这一阶段主要解决什么 |
| --- | --- |
| 01 最小计算闭环 | 跑通工具计算、程序验算与解释 |
| 02 自主反馈循环 | 模型根据结果，选择继续调用或结束 |
| 03 复杂任务处理 | 扩展工具、反馈参数错误、减少重复调用 |
| 04 四角色协作 | 分开职责、增加模型复核和角色交接记录 |
| 05 对话与会话体验 | 多轮上下文、身份、历史及模型后端选择 |
| 06 本次部署完善 | 独立管理服务，应用留内网，公网纯转发 |

### 画面怎么放

六阶段排为两行三格，各格只写“阶段名称 + 要解决的问题”。用编号体现顺序，把提交号和实现细节放在演讲者备注中。

### 建议讲解稿

从项目的实际演进看，第一步是让一次计算能够完成并被检查。随后才把固定链路改成自主循环，让模型根据结果继续选择动作。复杂题目会暴露参数错误、步骤重复和长回答不完整等问题，因此逐步扩展工具和反馈处理。接着引入四种角色，把求解、审查与汇总职责分开。再补普通聊天、多轮上下文、身份与历史会话，让它从演示逐步变成可使用的系统。本次又完善了服务常驻和公网转发部署。事件、人工审核与数据库在早期就已有基础，后续是在持续扩展。

### 开发历史依据（放备注，不要求学生记住）

- `eb8f0c8`：最小计算闭环，早期已有人工审核、SSE 和 SQLite。
- `54f23e3`：自主 decide → tool → verify → observe 循环。
- `275aefc` / `e802015` / `a98a86b`：长流程与复杂任务、工具扩展及汇总改善。
- `386f219`：四角色、模型复核和角色交接。
- `2eaaa39` / `539583d`：对话、会话及产品行为完善。
- 本次工作区：systemd、本地 Caddy、frp 和公网转发配置；此部分尚未提交。

### 学生带走的一句话

**逐步增加能力，同时让每一步更可检查、更容易维护。**

## 第 5 页｜设计取舍：自主性需要证据与边界

### 本页回答的问题

这个项目最重要的设计考虑是什么？当前还可以怎样改进？

### 屏幕上放什么

主标题：**自主性，需要证据与边界**。

三项设计原则：

- **允许做什么？** 工具白名单与参数校验。
- **结果凭什么？** 程序检查与模型复核。
- **过程怎么看？** 共享状态与执行事件。

三项下一步方向（明确标为改进方向）：

| 方向 | 当前边界 | 下一步完善 |
| --- | --- | --- |
| 完成条件 | 目标提示不硬性保证全部完成 | 将需求变成可核对的验收项 |
| 验证覆盖 | 部分工具仅做基础检查 | 加强交叉验证与反例测试 |
| 任务恢复 | 运行任务仍有内存状态 | 持久化检查点与恢复流程 |

补充一句：**当前角色骨架由代码规定，动态的是具体工具与后续动作。**

### 画面怎么放

上半页用三个简短问句呈现设计原则；下半页用三列对照展示“当前边界 → 改进方向”。不把计划表述成已经实现的能力。

### 建议讲解稿

开发 Agent 时，模型越能自主行动，程序就越需要规定范围、保留证据、记录过程。本项目采用工具白名单、参数校验、程序验算、模型复核和事件记录来支持这些要求。同时要清楚当前边界：目标提示并不能硬性保证每个要求都完成；不同工具的检查强度也不同；部分运行态仍在内存里，重启不能保证恢复所有未完成任务。后续应优先把验收条件、工具验证和任务恢复做得更扎实。当前模型自主选择工具与下一步动作，角色骨架仍由代码规定。

### 学生带走的一句话

**把自主决策与可检查的程序边界一起设计。**

## 核验说明

角色职责与通过条件依据 `backend/app/agents.py`；工具调用、角色交接与流程边界依据 `workflow.py`；模型工具协议依据 `llm.py`；历史记录依据 `storage.py`。开发阶段依据实际 Git 提交与本次部署工作区。本方案不宣称模型能任意创建角色、所有任务要求都被硬性保证完成，或全部运行任务可跨进程重启恢复。
